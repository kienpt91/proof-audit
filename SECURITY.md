# Security

## Reporting a vulnerability

Please use GitHub's private vulnerability reporting for this repository, or email kienphan.dev@gmail.com. Do not open a public issue for a vulnerability. This is a personal open-source project maintained on a best-effort basis: there is no service level and no bounty.

## What the tool is, and the safety boundary

`proof-audit` is defensive tooling. It reproduces access-control problems in **Postgres row level security** against a database it creates for the run, and nothing else. The boundary, enforced in code and tested:

- It connects only to (a) a container it starts itself, with no network at all, or (b) a PostgreSQL server on this machine's loopback interface that you name explicitly with `--database-url` or `--database-url-env`. Any other host is refused in the domain layer (`parseLoopbackUrl`), again in the adapter (`assertLoopbackHost`), and the URL grammar is strict: no `host=`/`hostaddr=`/`service=` options, no extra `@`, no DNS names, no short or octal IPv4 forms. Tests cover each. **Loopback does not prove that a server is a throwaway**: an SSH tunnel, a port-forward or a published docker port on 127.0.0.1 can lead to a real server. The tool therefore never switches to a server because of an environment variable, prints which server it is using, refuses a server that holds databases other than `postgres` unless you pass `--yes-this-is-throwaway`, creates two roles per run (removed afterwards) and runs everything from the project as one of them, without superuser rights.
- The docker daemon must be on this machine. The docker CLI honours `DOCKER_HOST` and the current context, so a `tcp:`, `ssh:` or `http(s):` endpoint is refused: it would run the migrations, which come from an untrusted project, on another machine.
- It makes no other network call during analysis. It does not scan live third-party systems.
- It never reads `.env` files, keys or production data. Input is plain SQL files you supply, a static-auditor JSON report, and its own evidence files. Seed data is synthetic (`alice@example.test`, `bob@example.test`, fixed UUIDs).
- It generates no attack tooling beyond SQL probes against the sandbox, run as `anon` and `authenticated` inside a sub-transaction that is rolled back.

## Threat model

The migrations under analysis are **untrusted**: they may come from a repository you have not reviewed.

**Trust domains** ([ADR 0011](docs/adr/0011-trust-domains-for-the-verdicts.md)). Three database roles: the *admin* (superuser) only runs statements written by this tool; the *migrator* (a non-superuser like Supabase's `postgres`) runs everything that comes from the project (migrations, seed rows, the proposed fix); the *prober* runs the probes. No function is stored in the database for the tool to call: every operation is an anonymous block built by the tool and sent in a session whose `search_path`, timeouts and `row_security` are pinned in the connection. Before the migrations, after them, after the probes and after the probes on the fix copy, the tool fingerprints the platform (the `auth.*` functions, roles, memberships, settings, event triggers); any difference, and any statement that touches protected objects, makes the run `INTEGRITY_VIOLATION` (exit code 4), every finding INCONCLUSIVE and the fix withheld.

| Threat | What the tool does about it | Residual risk |
| --- | --- | --- |
| Migration SQL forges a verdict by replacing the code that decides it (a harness function, a built-in shadowed through `search_path`, `auth.uid()`, a catalog row) | There is no stored helper to replace. The migrator is not a superuser, does not own the platform and cannot write the catalogs. Probe and catalog sessions are pinned and call only `pg_catalog`-qualified functions. Fingerprints and a scan of the migration text report any change or attempt as INTEGRITY_VIOLATION. Regression tests build each attack at run time against PostgreSQL 16.14. | A migration's own objects may answer differently for the synthetic users than for real ones (it can read the claims); a PostgreSQL privilege-escalation vulnerability would defeat the role boundary; the fingerprint covers what it lists. |
| Migration SQL reaches the network (`dblink`, `postgres_fdw`, `COPY ... PROGRAM`) | Default mode: container with `--network none`, no published port, `listen_addresses=''`. In any mode the migrator cannot use `COPY ... PROGRAM`, server-side files, large-object file functions, untrusted extensions or languages (tested). | In loopback mode the server's network is yours. |
| Migration SQL damages the host | Container: no capabilities, `no-new-privileges`, read-only root, tmpfs data directory, unprivileged user, 256 processes, 1 GiB memory, 1 CPU, no host mounts, `--pull never`, `--rm`. | A container escape would be a Docker vulnerability. |
| Migration SQL runs forever, floods the log, or resets its own timeout | `statement_timeout` 20 s, `lock_timeout` 5 s and an idle-transaction timeout are pinned in the session; every batch has a 120 s wall-clock limit after which the server-side sessions are terminated, not only the local client; the run has a 10 min budget; the container log is capped at 1 MiB and `log_min_messages=panic`. | A pathological run ends with exit code 3 and a clear message instead of partial results. |
| Containers left behind (crash, closed terminal, `kill -9`) | Removed in `finally`, on SIGINT/SIGTERM/SIGHUP/SIGQUIT, after an uncaught exception or rejection, by `--rm`, and at the next start (containers labelled `proof-audit=1` whose recorded pid is gone). | A killed process leaves its container until the next run or `docker rm`. |
| A table hidden from the audit (extension membership, dynamic SQL) | The catalog read skips only the database's own schemas and the shim's `auth.users`. | |
| Hostile identifiers, policy names, comments or messages in reports | Terminal output turns every control character, escape sequence, bidi override and zero-width character into a visible escape. Markdown output escapes markup, HTML, links, mentions, pipes and newlines, uses code spans and fences longer than any backtick run in the content. Generated SQL writes unsafe identifiers and literals as `U&"..."` Unicode escapes so `fix.sql` is safe to print. JSON keeps text as found (JSON escapes control characters); a program that renders it must sanitise it for its own sink. | Text you paste elsewhere is your responsibility. |
| Hostile or oversized input files, links in the output directory | Files are opened with `O_NOFOLLOW`/`O_NONBLOCK` and checked on the descriptor. Output files are opened with `O_NOFOLLOW`/`O_NONBLOCK` too, so a checkout that contains `report.md -> ~/.zshrc` is refused. Caps: 1 MiB per SQL file, 4 MiB and 500 files in all, 20 000 statements, 256 KiB per statement, 8 MiB per JSON input, 300 tables, 5 000 probes. A cap makes the run `complete: false`. | A symbolic link in a parent directory of `--out` is followed (the directory itself is checked). |
| Forged or edited evidence | `proofs.jsonl` is decoded with a strict schema, per-proof hashes are recomputed and the recorded inputs are re-hashed. The hashes are unkeyed, so **`verify` does not trust the file for anything it executes**: it regenerates the probes and the fix from the migrations with its own planner and refuses (exit 2) a file whose SQL, claims or fix differ; recorded input paths cannot contain `..` and are only read from inside `--root`. `verification-contract.json` accepts only `proof-audit verify ...` commands with plain or single-quoted words. | A hash proves integrity, not authorship; evidence is not signed. |
| A forged, edited or stale `findings.json` | `findings.json` (the export in the findings.json format, [docs](docs/findings-json.md)) is **derived output**: `verify` never opens it, the hashes of `proofs.jsonl` do not cover it, and nothing re-computes it. Its records cite the probes behind them by id and content hash, so a claim can be checked against `proofs.jsonl` and replayed. It is written only if it conforms to the format (checked on the exact text) and every position in it is a real line of the migrations; otherwise it is skipped with a message. | A copy somebody edited reads like any other JSON file: do not trust a `findings.json` you did not produce, regenerate it from the migrations. |
| What `findings.json` contains | File paths of the migrations as displayed (the format requires safe repository-relative paths, so an absolute path, `..`, `:` or a control character in an input path means no file is written); the exact SQL of the proven probes, the proposed fix and the claims of the probes, all with synthetic values; names from your migrations; the database's SQLSTATE and message truncated to 300 characters. **Nothing is redacted or escaped**: text from your repository is kept as found, exactly like `report.json`, and the tool prints its own notes about the file through the terminal sanitizer. The tool adds no secrets: it never reads `.env` files, keys or production data, so only what your migrations themselves put into table, policy and file names can appear. | A program that renders the file must sanitise it for its own sink. |
| Ambient environment | `DOCKER_HOST`/context pointing off-machine is refused; `PROOF_AUDIT_DATABASE_URL` is not read implicitly; a password in `--database-url` triggers a warning (it is visible in the process list), `--database-url-env` avoids it. | |
| Secrets in logs | No secret is read or logged. A refused database URL is never echoed. Test passwords are generated at run time and kept in a mode-600 file that is removed on exit. The repository has a secret scanner in the pre-commit and pre-push hooks and in CI. | |
| Docker daemon access | Docker is called with fixed argument vectors through `spawn` with `shell: false`; nothing from the analysed project is ever part of an argument. | Anyone who can run docker can already do far more. |

### What is and is not guaranteed

Guaranteed, given an intact PostgreSQL and container: a probe verdict is the database's own answer to a statement written by this tool, in a session the migrations could not configure, and the objects that SQL depends on in the platform were checked before and after. A false CLEAN or false PROVEN produced by a migration replacing tool or platform code is not possible; an attempt is reported as INTEGRITY_VIOLATION.

Not guaranteed: that a project's own objects behave the same for the synthetic users as for real ones; protection against PostgreSQL or Docker vulnerabilities; that a migration cannot slow a run down; that results are meaningful when the Supabase shim differs from your project.

## Limitations

What the tool proves is limited to row level security logic in the SQL you give it, against two synthetic users and an anonymous caller. It does not check application-layer authorization, frontends, secrets exposure, storage buckets, realtime or any live system; a CLEAN result is not a penetration test. The Supabase shim is an approximation, seeding is heuristic, and PostgreSQL version differences can change outcomes. The README lists these in detail.

## Dependency policy

- One runtime dependency, `pg`, used only by the loopback transport; everything else is a development dependency. `files` in `package.json` is limited to `dist`.
- Exact pins in `package.json` and a committed `package-lock.json`. Every package, direct and transitive, was resolved with `npm install --before=2026-10-24T00:00:00Z --ignore-scripts`; `check-age` reports zero packages newer than the cutoff. Installs, tests and builds run in throwaway containers; CI uses `npm ci --ignore-scripts`. No dependency needs an install script.
- Container images (Node 22 and 24, PostgreSQL 16.14) are pinned by digest; GitHub Actions are pinned to full commit SHAs. Dependabot (npm and github-actions, weekly, 7-day cooldown) ignores major bumps of `typescript` and `@types/node`.

## Open advisories

`npm audit` reports no advisories at the cutoff, with and without `--omit=dev` (see the README).
